Prompt Engineering

Системна постановка задач для LLM — архітектура запитів, що дають передбачувані результати. Фундамент для будь-якої AI-автоматизації.

System Prompt Zero / Few-shot Chain of Thought Output Format Role Prompting

Що таке Prompt Engineering?

LLM (великі мовні моделі) — це статистичні машини передбачення наступного токена. Вони не «розуміють» завдання — вони шукають найімовірніше продовження введеного тексту.

Prompt Engineering — мистецтво і наука формулювання вхідного тексту так, щоб модель «продовжила» його саме так, як потрібно.

💡
Ключова ідея

Зміна одного слова в промпті може кардинально змінити відповідь. Промпт — це не «прохання», це специфікація поведінки.

Чому це важливо для CAIO?

🔧 Автоматизація

В Make.com/n8n AI-модуль отримує промпт автоматично. Від якості промпту залежить весь сценарій.

💰 Вартість

Чіткий промпт = менше токенів на виправлення помилок = менша вартість API-запитів.

🎯 Точність

Клієнтські AI-рішення мають давати передбачуваний результат. Промпт — головний інструмент контролю.

🔄 Масштаб

Один добре написаний промпт обробляє тисячі запитів без ручного втручання.

Як мислять LLM

Модель бачить весь твій текст як один потік — вона не відрізняє «інструкцію» від «даних», якщо ти явно не розмежуєш їх. Тому структура промпту критична.

Концептуально
# Модель "думає" так:
"Даний мені текст + відповідь, яка з найбільшою
ймовірністю йде після нього в корпусі навчання"

# Тому промпт з прикладами (few-shot) працює краще:
Вхід: "погана служба"      → Тональність: Негативна
Вхід: "швидко доставили"  → Тональність: Позитивна
Вхід: "зламалось через тиждень" → Тональність: ???

# Модель "продовжить" паттерн → Негативна
⚠️
Типова помилка

Писати промпти як Google-пошук: «summarize this article». LLM потрібен контекст, роль, формат і обмеження.

Анатомія промпту

Повноцінний промпт для виробничої системи складається з кількох компонентів. Не всі обов'язкові для кожного запиту — але знати їх треба.

👤
ROLE
Хто є модель у цьому контексті. Задає «голос» та область компетентності відповіді.
🎯
TASK
Конкретне завдання. Дієслово + об'єкт: «Проаналізуй», «Перефразуй», «Класифікуй».
📋
CONTEXT
Чому, для кого, в якій ситуації. Без цього модель заповнює прогалини припущеннями.
📥
INPUT
Дані, що обробляються. Чітко відокремити від інструкцій — розмітка, теги, роздільники.
📤
OUTPUT FORMAT
Як має виглядати результат: JSON, список, таблиця, довжина, мова, тон.
🚫
CONSTRAINTS
Що НЕ робити. Explicit негативні інструкції часто ефективніші за позитивні.
📚
EXAMPLES
Few-shot приклади «вхід → вихід». Найпотужніший інструмент для специфічних форматів.

System vs User prompt

В API-запитах є два окремих «слоти». Це ключова архітектурна концепція для автоматизації.

API структура 
{
  "model": "gpt-4o",
  "messages": [
    {
      "role": "system",              ← постійні інструкції
      "content": "Ти аналітик..."   ← поведінка, формат, роль
    },
    {
      "role": "user",                ← змінні дані
      "content": "Проаналізуй: {{data}}" ← конкретний запит
    }
  ]
}
✅
Правило розділення

System = що модель є і як поводиться (постійно). User = що конкретно обробити (змінюється кожен запит). В автоматизації system фіксований, user — шаблон з підстановкою {{змінна}}.

Реальний приклад для Make.com

Виробничий промпт 
// SYSTEM
Ти — асистент класифікації звернень клієнтів.
Завжди відповідай ТІЛЬКИ валідним JSON.
Без пояснень, без markdown, без зайвого тексту.

Схема відповіді:
{
  "category": "billing|technical|shipping|other",
  "priority": "low|medium|high|urgent",
  "sentiment": "positive|neutral|negative",
  "summary": "1 речення українською"
}

// USER (шаблон з підстановкою)
Класифікуй це звернення:
---
{{1.text}}
---

Основні техніки

1 · Zero-shot

Пряма інструкція без прикладів. Працює для простих та зрозумілих завдань.

Порівняння
// ❌ Погано:
Summarize this.

// ✅ Zero-shot правильно:
Підсумуй наступний відгук клієнта у 1 реченні.
Фокус: головна проблема або похвала.
Відповідь — лише речення, без вступу.

Відгук: "{{customer_review}}"
2 · Few-shot

Надаєш 2–5 прикладів «вхід → очікуваний вихід». Найефективніша техніка для специфічних форматів.

Шаблон
Класифікуй тональність. Приклади:

Вхід: "Доставка тиждень — жахливо!"
Вихід: негативна

Вхід: "Нормально, але могло бути краще"
Вихід: нейтральна

Вхід: "Перевершили очікування!"
Вихід: позитивна

---
Вхід: "{{user_text}}"
Вихід:
3 · Chain of Thought (CoT)

Просиш модель «думати вголос» перед відповіддю. Різко підвищує якість для складних логічних завдань.

Шаблон
Перед відповіддю міркуй крок за кроком:
1. Яка головна проблема клієнта?
2. Чи є вона технічною, біллінговою чи сервісною?
3. Наскільки термінова (є ризик відтоку)?

Після міркування → дай відповідь у форматі JSON.

// Або коротко:
Подумай крок за кроком, потім дай відповідь.
4 · Role Prompting

Задаєш конкретну роль з компетентністю та тоном. Змінює «голос», рівень деталізації і термінологію.

Порівняння
// ❌ Слабо:
Ти — помічник.

// ✅ Сильно:
Ти — досвідчений customer success менеджер
в SaaS-компанії. Твій пріоритет — утримання
клієнтів. Говориш про рішення, не виправдання.
Тон: теплий, але конкретний.
5 · Output Formatting

Точна специфікація формату виводу — обов'язкова для автоматизації. Наступний модуль парсить результат програмно.

Шаблон
Відповідай ЛИШЕ у форматі JSON. Без ```json.
Без пояснень. Без додаткового тексту.

Структура:
{
  "result": string,    // головний висновок
  "tags":   string[],  // масив 2-5 тегів
  "score":  number     // від 0 до 10
}

Порівняння технік

Техніка Коли використовувати Токени Якість
Zero-shot Прості, очевидні завдання ↓ мало Базова
Few-shot Специфічний формат / класифікація ↑ більше Висока
CoT Логічний аналіз, складні рішення ↑↑ багато Дуже висока
Role Тон, стиль, компетентність ↓ мало Добра
Format Завжди в автоматизації ↓ мало Критична
💸
Оптимізація вартості

Few-shot з 5 прикладами може коштувати в 2–3× більше, ніж zero-shot. Знаходь баланс точності та вартості для кожного сценарію.

Конструктор промпту

Збери свій промпт для сценарію автоматизації. Результат — готова структура system + user для Make.com або n8n.

⚡ PROMPT BUILDER ~0 токенів
🔧
Для Make.com

Частину SYSTEM → у поле «System prompt» AI-модуля. Частину USER → у «User message» з підстановкою {{1.text}} замість плейсхолдера.

Перевірка знань

Вибери одну відповідь для кожного питання, потім натисни «Перевірити».

1. Яка головна відмінність System prompt від User prompt в API?
System prompt обробляється швидше
System — постійна поведінка та роль, User — змінні дані для обробки
Вони ідентичні, різниця лише в назві
User prompt коштує більше за токенами
2. Яку техніку найкраще застосувати, коли важливий специфічний формат виводу?
Zero-shot — він найдешевший
Few-shot з прикладами «вхід → вихід»
Chain of Thought — він завжди кращий
Role prompting — задай роль класифікатора
3. Чому важливо явно вказувати формат виводу (JSON тощо) в автоматизації?
Для краси — людині зручніше читати
Щоб заощадити токени
Наступні кроки сценарію парсять результат програмно
Модель ігнорує інструкції без вказаного формату
4. Chain of Thought (CoT) підвищує якість тому, що...
Зменшує кількість токенів у відповіді
Змушує модель будувати проміжні висновки перед відповіддю
Дозволяє пропустити few-shot приклади
Прискорює генерацію відповіді
5. В system prompt написано: «Ти — customer success менеджер. Тон: теплий але конкретний. Фокус на рішеннях.» Яка це техніка?
